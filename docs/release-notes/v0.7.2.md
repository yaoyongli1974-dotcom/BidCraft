# BidCraft v0.7.2

技术标写完之后，团队里通常要过三道人：技术负责人看技术，商务负责人对报价口径，投标经理
最后放行。本版把这三道关做成章节级、不可绕过的检查点。

## 本版内容

- **章节状态流转**：草稿 → 待复核 → 已确认 → 已锁定。
  - 编辑（项目成员）可以「提交复核」；
  - 项目负责人/超管「确认通过」「锁定」「撤回」；
  - 撤回已确认、解锁已锁定必须填原因（至少 4 个字），原因与操作人写入审计
    （`chapter.review`，含 from/to）。
- **已确认与已锁定 = 正文冻结**：保存、重新生成一律拒绝，并提示「需先撤回为草稿」。
  「锁定」是最终交付态：要再动必须负责人先解锁、再撤回，每一步都留痕。
- **待复核期间改正文 = 自动退回草稿**：复核对象一旦变化，检查点立即失效——不会出现
  「负责人确认的是 A 版、导出的是 B 版」。保存审计里带 `review_reverted` 标记。
- **导出只读取已确认的章节**：存在草稿/待复核的有正文章节时，docx/pdf/md 返回 409，
  文案列出未确认数量与章节名；全部确认后才放行。`xlsx`（事实台账）不受限。
  **强制导出也绕不过这道门**——它只能覆盖「未处置的废标/阻断风险」，人工确认必须真做。
  `bidcraft run`（一条命令解析→生成→导出，没有复核环节）是唯一例外；
  **批量导出**同样逐项目过门禁，未确认的项目记入失败清单、其余照常打包（后台批量没有 force 通道）。
- **界面**：章节头部显示复核状态与确认人/锁定人；右侧章节列表给非草稿章节加状态徽章；
  冻结时编辑器与保存/生成按钮同步禁用。需要填原因的动作弹窗输入，不足 4 字无法提交。
- **接口**：`POST /projects/{ref}/chapters/{node_id}/review`（body `{action, note}`），
  `GET /projects/{ref}/chapters/{node_id}` 与 `/outline` 增加 `review_status`、
  `review_requested_*`、`confirmed_*`、`locked_*` 字段。

## 说明

- 不引入 BPMN 或可配置流程：就是四个状态、五个人工动作，规则写死在服务端。
- 已有项目升级后，既有正文一律视为**草稿**（不会被误当成「已确认」），
  需要团队逐章确认后才能导出——这是有意的：历史正文没人签过字。
- 数据库增量列由启动时的幂等迁移自动补齐（`sections` 表 8 列）。
