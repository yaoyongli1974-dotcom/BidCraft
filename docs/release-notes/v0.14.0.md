# BidCraft v0.14.0

本版只做一件事：把上一轮审查指出的「第一层架构收尾」做完。`api/app.py` 长期承担着两副重担——既是最初单文件时代的全部请求模型与 helper 定义地，又是按域拆路由后遗留的共享命名空间。这一版把「定义」与「门面」彻底分开。

## 本版内容

- **请求模型外迁**：71 个 Pydantic `BaseModel`（`ProjectCreate`、`ChapterReview`、`KbCreate`……）从 `app.py` 搬到新文件 `api/schemas.py`，按纯数据定义组织，无副作用。
- **共享层下沉**：helper、常量、以及从底层模块 re-export 的 runner/helper 别名迁到新文件 `api/shared.py`，作为路由与门面的单向依赖源，并显式列出 `__all__`。
- **`app.py` 瘦身**：从 **1933 行降到 793 行**，只剩两样东西——`create_app()` 组装器（注册中间件与 12 个域路由）和一个兼容门面（`from .shared import ...` 的中性重导出）。
- **路由反向依赖解耦**：12 个路由模块统一改为 `from ..shared import ...` / `from ..schemas import ...`，不再 `from ..app import ...`。依赖方向从 `routes ↔ app` 双向耦合变成 `routes → schemas/shared → 底层` 单向。

## 为何保留 app 门面（没有删掉它）

门面不是残留的债，而是刻意保留的兼容层，有三条硬约束：

1. `from bidcraft.api import create_app` / `import bidcraft.api` 的既有调用方（CLI、全部测试）零改动。
2. 多处测试 `monkeypatch.setattr(api, "_run_kb_reindex_job" / "MAX_TENDER_UPLOAD_BYTES" / "reset_current_user", ...)` 依赖门面上的名字。
3. `jobqueue._runner_for` 通过 `sys.modules["bidcraft.api.app"]` 在运行期解析 runner 名，所以门面导出的 runner/helper 必须与 `workers` / `services` 是**同一个对象**。

`test_api_package.py` 与 `test_worker_extraction.py` 守护这些不变量：门面保留全部导出名、runner/helper 对象同一、194 条路由总数不变、模型只在 `schemas.py`、路由不再反向依赖 `app`。

## 兼容性

- **URL、请求体、响应格式全部不变**：`create_app()` 逻辑一行未动，路由函数体一行未动，只是 import 来源换了。
- monkeypatch 语义不变：门面 re-export 与底层同源对象，运行期查找照常命中。
- 前端零改动。
