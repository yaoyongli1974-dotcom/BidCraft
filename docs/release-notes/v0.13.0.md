## 任务执行幂等保护

- **章节级幂等账本**：已完成章节写入 `Job.payload['done_steps']`（形如 `chapter:<node_id>`），
  随 Job 行持久化，**跨重排队、跨服务重启保留**。租约过期被回收后新 worker 认领重跑时，
  `generate_document` 通过 `before_chapter` 钩子跳过已完成单元，只对未完成章节调用模型。
- **中止检查点**：心跳线程发现租约被回收（条件 UPDATE 零行）时设置 `abort` 事件；
  runner 在章节边界与流式输出（`on_delta`）调用 `raise_if_aborted()` 立即抛出 `JobAborted`，
  旧 worker 不再继续烧 token、不再写正文。中止任务由 `_finalize_after_run` 退回 `queued`，
  **不写 failed、不触发退款**，由下一个 worker 从账本续跑。
- 章节正文写入与账本标记在**同一数据库事务**中提交（`after_chapter` 复用 writer 的 session），
  不会出现「正文写了但账本没记」导致的重复。

## Worker 优雅退出

- SIGTERM / SIGINT（`bidcraft serve` 与 `bidcraft worker` 均注册）调用 `request_shutdown()`：
  停止认领新任务、唤醒空闲 worker、通知在途 runner 在检查点收尾。
- FastAPI 应用通过 lifespan 在 HTTP drain 完成后 drain worker（`wait_for_workers`，超时
  `BIDCRAFT_SHUTDOWN_GRACE_SECONDS`，默认 30s）；API-only 部署不误触发。
- 退出有上限，不会永久阻塞；进程被硬杀（kill -9）时仍由租约超时 + reaper 恢复，
  与既有的 at-least-once 语义一致。

## 验收标准对照

- **两个 Worker 并发**：认领是单条条件 UPDATE，同一 Job 只能被一个 worker 拿到；fencing
  令牌使旧 worker 的关键写入失效。
- **服务重启**：启动恢复只动已过期租约；在途任务由 reaper/恢复退回队列并从账本续跑。
- **租约过期**：独立 reaper 按时回收；心跳丢失即置 abort，旧 worker 在章节边界停止。
- **心跳失败**：条件 UPDATE 零行 → abort → 中止任务退回队列；不会与 worker 状态互相覆盖。
- **不重复副作用 / 不覆盖状态**：幂等账本跳过已完成章节；fencing 拦截所有过期写入与退款。

语义仍是 **at-least-once**：极窄竞态窗口内（租约刚丢失、abort 尚未传播）当前章节可能重跑一次，
账本保证不会跨章节重复；这是不引入分布式事务/两阶段提交的工程取舍。
