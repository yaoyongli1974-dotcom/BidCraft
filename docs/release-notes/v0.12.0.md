# BidCraft v0.12.0

本版把任务队列的两处部署隐患一起收口：reaper 不再被忙队列饿死；API 与 Worker
可以真正分进程部署，API 重启不再影响任务执行。

## 1. Reaper 独立常驻线程（P1）

旧结构里 `reap_expired()` 只在 worker 的「没领到任务」空闲分支执行。只要队列持续有任务，
或者所有 worker 都卡在长任务里，过期租约就可能长期无人回收，失败的任务被无限期挂起。

- 新增 `_reaper_loop()`：启动即回收一次，之后每 30 秒回收一次，与 worker 是否空闲无关。
  等待用 `_stop.wait(interval)`，服务停止时立即退出。
- 单实例守护：`_start_reaper()` 幂等；`_reset()` 同步清理标志。
- worker 循环精简为「认领 → 执行」，并加结构守护断言，防止回收逻辑被搬回去。

## 2. API / Worker 分离部署（P1）

此前 `create_app()` 在每个进程启动时都做任务恢复，`submit()` 又会在 API 进程里
懒启动 worker。这在 `uvicorn --workers N` 下会导致多个 API 实例各自恢复、各自跑任务。

- **`create_app()` 变为纯应用工厂**：不再执行恢复，避免 ASGI 多实例互相影响。
- **恢复移入 worker 进程入口**：`bidcraft serve`（单进程）与新增的 `bidcraft worker`
  都显式调用 `recover_on_startup()`。即使多个 worker 进程各跑一次，也只动已过期租约
  （与 reaper 同口径），不会把别的 worker 正在执行的任务重新排队。
- **`BIDCRAFT_EMBEDDED_WORKERS=0`**：API 进程只把 Job 写入数据库，不拉起本地 worker、
  不执行任务；独立的 `bidcraft worker` 进程负责认领与执行。默认仍为 `1`，
  即 `bidcraft serve` 的单进程行为完全不变。

### 两种部署方式

```bash
# 方式 A：单进程（开发 / 小规模，保持原样）
bidcraft serve --host 0.0.0.0 --port 8000

# 方式 B：API 与 Worker 分离（生产 / 需要独立扩容）
BIDCRAFT_EMBEDDED_WORKERS=0 uvicorn bidcraft.api:app --host 0.0.0.0 --port 8000 --workers 4
bidcraft worker          # 可起 1..N 个进程，各自原子认领
```

API 进程重启不影响 worker 生命周期；worker 独立扩容。仍使用 SQLite，无需引入 Redis。
worker 进程发现新任务的延迟为其空闲轮询间隔（默认 5 秒）。

## 验证

- 新增 4 例：忙队列下过期租约仍被独立 reaper 回收、worker 循环不含 reaper、
  `embedded_workers=False` 时 submit 不拉起 worker、`create_app()` 不触发恢复。
- 全量 **841 passed**（837 + 4），ruff 全绿；web 169 tests / lint 0-0 / build 0。
- 语义不变：仍是 at-least-once（见 v0.11.1）；fencing 令牌继续保证旧 worker 写不进新任务。
