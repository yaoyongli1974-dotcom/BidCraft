# BidCraft v0.11.0

把任务队列从「进程内存里的堆」搬到「数据库里的 Job 行」。这项改造解决一个根本不一致：
过去任务数据在 SQLite 持久化、待执行任务却在 Python 进程内存中，两者对不上。

## 为什么改

- 服务若在「数据库建好 Job」与「内存 submit()」之间崩溃，内存任务丢失，数据库里留下一个永远没人执行的 queued Job。
- 服务重启时 `_recover_interrupted_jobs()` 把所有 queued/running 一律标失败——一个跑到第 25 分钟的 40 分钟标书生成任务，重启后直接判死。
- 多进程部署（`--workers 4` 或多实例）各进程有各自的堆，数据库虽共享但队列不共享，同一任务可能被重复执行。
- 没有背压：排队任务数无上限，也没有单用户配额。

## 本版内容

**DB 成为队列唯一真源**：`jobs` 表里 `status='queued'` 的行就是队列。建 Job 并提交即完成入队，消除了「提交与入队两步之间崩溃」的窗口。Worker 用**条件 UPDATE**（`WHERE id=(SELECT … queued ORDER BY priority, created_at LIMIT 1) AND status='queued' … RETURNING`）原子认领——多进程/多实例下只有一个能抢到同一行，不会重复执行。

**租约 + 心跳 + 重排队恢复**：Worker 认领后写 `lease_expires_at`，执行期间由心跳线程每 60 秒续租；进程崩溃时租约过期，reaper 把任务重新排队并 `attempts+1`，超过 `max_attempts`（默认 3）才判失败。启动恢复不再一律标失败，而是把孤儿 running 任务重排队、queued 保持原样。**诚实边界**：这是从头重跑，不是从第 25 分钟断点续跑；逐章检查点续跑另立专项。

**DB 驱动派发**：新增按 `job.kind` 的中央派发表，Worker 从 `job.payload` 重建 runner 参数（批量核对/导出、正文生成、配图、知识库索引）。`kb_reindex` 原先的裸线程也纳入统一派发。派发保留运行期 monkeypatch 查找，测试注入的 runner 仍然生效。

**背压**：新增全局排队上限（`BIDCRAFT_MAX_QUEUED_JOBS` 默认 100）与单用户配额（`BIDCRAFT_MAX_USER_QUEUED_JOBS` 默认 10），入队时检查，超限返回 429。另加租约/心跳/重试次数配置项。

**数据库迁移**：新增 Alembic revision `0003_job_queue`，为 `jobs` 表幂等增加 `attempts/max_attempts/claimed_at/lease_expires_at/heartbeat_at/worker_id` 六列与租约索引。

## 说明

- 仍是模块化单体 + 独立任务 Worker，**没有**引入 Redis/PG/Celery，也不搞微服务——为未来拆独立 Worker 铺垫，但不提前上分布式。
- `queue_position` 语义保持：改为按 priority + created_at 数数据库里排在前面的 queued 行。
- 显式失败（例如台账缺项）不重试，避免刷屏；只有「意外中断/租约过期」才走重排队。
