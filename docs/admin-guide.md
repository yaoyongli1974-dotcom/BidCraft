# 管理控制台与权限

BidCraft 的 Web 部署内置登录、会话与角色权限。超级管理员在 `/admin` 配置模型、知识库与规则包，普通成员按角色使用项目。

## 首次登录

首次启动时自动创建一个超级管理员：

```bash
BIDCRAFT_ADMIN_PASSWORD='替换为强密码' bidcraft serve --host 0.0.0.0 --port 8000
```

- 用户名由 `BIDCRAFT_ADMIN_USER` 指定，默认 `admin`。
- 未设置 `BIDCRAFT_ADMIN_PASSWORD` 时，系统生成随机密码并写入
  `BIDCRAFT_HOME/initial-admin.txt`（权限 0600），该文件只生成一次。
- 忘记密码可在服务端离线重置：

```bash
bidcraft reset-password admin
```

密码至少 8 位；修改密码会注销该用户的全部会话。

## 角色

| 能力 | 超级管理员 | 投标经理 | 只读成员 |
|---|---|---|---|
| 查看项目、台账、正文、核对结果 | ✓ | ✓ | ✓ |
| 创建/删除项目、导入解析、编辑、生成、核对、导出 | ✓ | ✓ | — |
| 模型、知识库、规则包、用户与权限管理 | ✓ | — | — |

后端对每个写请求校验角色，前端的禁用状态只是提示，不能替代权限校验。
至少保留一个启用状态的超级管理员；不能删除、停用或降级当前登录账号。

全局角色之外还有**项目级成员**：项目负责人（owner）可在项目「协作」页签添加
投标经理/只读成员为 editor/viewer。editor 可编辑该项目，viewer 只读（写请求 403）；
非成员访问他人项目返回 404。超级管理员可访问全部项目。成员管理与删除项目仅 owner
或超级管理员。章节保存带 revision 乐观锁，冲突时前端提示载入最新或强制覆盖。

## 模型配置

`/admin` → **模型配置** 支持三类模型：

- `chat`：大纲与正文生成使用；取“默认且启用”的对话模型，没有默认时取最近更新的启用模型。
- `image`：章节配图使用；取“默认且启用”的图片模型。正文页可按章节填写画面描述、风格、
  尺寸并生成，也可上传 PNG/JPEG 或重新生成；项目图库可跨章节复用图片，配图计划汇总
  各章占位的已匹配/失败/缺失情况，并可按计划后台批量生成缺失/失败配图。配图计划还会
  按章节字数计算预算，默认每 3000 字 1 张、每章最多 4 张，可用
  `BIDCRAFT_IMAGE_WORDS_PER_IMAGE` / `BIDCRAFT_IMAGE_MAX_PER_CHAPTER` 调整。
  「按计划插入」只替换已匹配且未超预算的占位，并直接保存章节正文。
  正文页另有「整篇配图策略」折叠面板：全文配图上限（0=不限，默认 12）、批量生成默认
  风格/尺寸、图注开关与编号前缀、DOCX 版心宽度（8–19cm）。策略存于项目 meta，
  「生成并插入」会先批量补齐缺失/失败图、完成后自动按计划插入；导出 DOCX/PDF 按策略
  设置图宽并跨章累计图注编号（`图N　图名`）。
- `embedding`：为本地知识库提供向量语义检索；未配置时知识库自动使用关键词召回。
- `BIDCRAFT_VERDICT_LLM=1`：实质性条款判定启用可选 LLM 语义匹配器（`verdict_llm.py`），
  仅用于判断正文是否正面应答条款；无模型配置、调用失败或单次核对超过 200 次调用时自动回退规则匹配，
  数值/等级/日期/否定仍由确定性规则裁决，LLM 不能单独把条款判为 SATISFIED。

字段：

| 字段 | 说明 |
|---|---|
| 名称 | 控制台内唯一标识 |
| 类型 | `chat` / `image` / `embedding` |
| 提供方 | `openai`（OpenAI 兼容）、`ollama`、`custom` |
| Base URL | 例如 `https://api.openai.com/v1`、`http://127.0.0.1:11434/v1`、`http://ollama:11434` |
| 模型名 | 端点实际模型 ID |
| API Key | 加密后写入数据库，接口只返回“密钥已配置”；编辑时留空表示不修改 |
| 温度 / 最大输出 | 生成参数 |
| 默认 | 同类型只能有一个默认模型，默认模型必须启用 |

图片模型可在 `options` 中设置生成默认值：

| 键 | 说明 |
|---|---|
| `image_size` | 默认尺寸，如 `1024x1024`；请求未指定尺寸时使用，仍为空则回退 `1024x1024` |
| `image_quality` | 可选，写入图片请求的 `quality`（如 `standard` / `hd`，以供应商支持为准） |
| `response_format` | 默认 `b64_json`；设为空字符串时不在请求中发送该字段，由端点决定返回格式 |

生成端点按 OpenAI 兼容的 `POST {Base URL}/images/generations` 调用，支持返回 `b64_json`
或临时 `url`（服务端下载后校验 PNG/JPEG）。图片模型连通性测试只验证端点/鉴权，不实际
发起生成请求，避免产生费用；实际生成由用户在章节配图面板触发。

连通性测试：

- OpenAI 兼容：请求 `GET {Base URL}/models`；若不可用，对话模型回退到最小
  `POST /chat/completions`，向量模型回退到 `POST /embeddings`。
- Ollama：请求 `GET {Base URL}/api/tags`。

API Key 使用 `BIDCRAFT_HOME/secret.key` 加密。迁移或备份时必须同时保留
`bidcraft.db` 与 `secret.key`，否则已保存的密钥无法解密。

## 知识库

`/admin` → **知识库** 支持两种接入：

### 本地目录

- 填写服务端可读目录，递归索引 `.pdf` `.docx` `.txt` `.md` `.markdown` `.xlsx` `.xlsm`。
- 单文件上限 25 MB，最多 500 个文件；知识库索引不执行 OCR，扫描版 PDF 需先转成可复制文本
  （招标文件解析链路已可选支持 `pdftoppm + tesseract`，不影响知识库索引）。
- 点击“重建索引”后写入 SQLite，按 900 字片段、120 字重叠切分。
- 检索默认使用中英文字符 bigram 重叠评分，无需额外向量服务；适合规范、产品手册、
  施工方案等中小规模资料。
- 配置 embedding 模型后，重建索引会同时构建向量索引，也可单独点击“构建向量”。
  检索按「(1-权重)×关键词分 + 权重×余弦相似度」混合重排；换模型后旧向量自动失效，
  需重新构建。未配置模型、向量构建失败或查询嵌入失败时自动回退关键词召回，不阻断生成。
- 向量相关环境变量：`BIDCRAFT_KB_VECTOR`（默认开）、`BIDCRAFT_KB_VECTOR_WEIGHT`（默认 0.6）、
  `BIDCRAFT_KB_VECTOR_MIN_SCORE`（默认 0.1）、`BIDCRAFT_KB_VECTOR_MAX_CHUNKS`（默认 4000，0 不限）、
  `BIDCRAFT_KB_VECTOR_BATCH`（默认 16）。
- 修改目录后需重新建索引，旧片段会自动清除。

### 第三方 API

选择 `generic`、`dify` 或 `ragflow`，填写地址、密钥和可选数据集 ID。

**通用接口** `generic`：

```http
POST {location}
Authorization: Bearer <api_key>
Content-Type: application/json

{"query": "综合布线测试", "top_k": 4}
```

响应支持 `results` / `data` / `documents` 数组，元素使用
`content|text|answer|snippet` 与 `title|source|document_name` 字段，`score` 可选。

**Dify**：`location` 填 API 根地址（如 `https://api.dify.ai/v1`），
系统请求 `POST /datasets/{dataset_id}/retrieve`，读取 `records[].segment.content`。

**RAGFlow**：`location` 填 API 根地址（如 `http://host/api/v1`），
系统请求 `POST /retrieval`，读取 `data.chunks`。

检索失败不会阻断正文生成，只会跳过该知识库。知识库内容作为“参考背景”注入
提示词；资质、业绩、价格、人员与参数仍以事实台账为准，缺失时保留 `{{待填:...}}`。

## 规则包

`/admin` → **规则包** 管理新建项目可选的行业规则包。内置包位于
`bidcraft/resources/packages/`，不会被后台直接改写；管理员修改写入
`BIDCRAFT_HOME/packages/<name>.yaml`，同名覆盖内置包。内置包仍保持可恢复。

- 支持的 `project_type`：弱电智能化、消防工程、安装工程、土建工程、暖通空调、
  装饰装修、其他；通用基包为 `common`，不显示在新建项目列表。
- 新建规则包时可填写「规则包名称」（显示名）、「包名」（唯一标识）并选择「工程类型」；
  这三项会同步写入 YAML 的 `title`、`package`、`project_type` / `project_type_label`。
- 新建项目按项目类型分组展示规则包；创建后不能换包，换包请新建项目。
- 保存前完整校验 YAML、继承链、字段、章节大纲与核对表达式；校验失败不会落盘。
- 「删除」只把包写入 `hidden.json`，从新建项目列表隐藏；已有项目继续加载，
  新项目即使直接调用 API 也会被拒绝。被项目引用时后端拒绝删除并提示引用数量。
- 「恢复」取消隐藏；「恢复内置原文」删除用户覆盖文件，回到随程序发布的内置版本。
- 包名（唯一标识）只能是 `[a-z][a-z0-9-]{0,63}`，YAML 的 `package` 必须与包名一致；
  显示用的「规则包名称」可自由填写，保存在 YAML 的 `title`。

## 批量操作与标段

- 项目列表支持多选（含全选），批量条提供**批量核对**与**批量导出**（docx/md/xlsx）。
  两者均为后台任务：逐项目执行，单项失败只记结果不中断；完成后核对结果逐项目展示，
  导出结果打包为 zip 自动下载（存于 `BIDCRAFT_HOME/output/`）。
- 批量操作仅对当前用户有权限的项目生效（owner/成员/超管），全局只读角色不可发起；
  单次最多 50 个项目。
- 项目可填写**标段/包件**（≤60 字，新建弹窗或项目编辑），列表按标段筛选与展示 Badge；
  标段作为组织标签保留，项目内更细的多包件清单位于清单页（见下节）。

## 包件（标段/包件清单）

同一项目可按标段/包件维护多份独立工程量清单；**事实台账与材料表仍是项目级共享**，不随包件复制。

- 清单页顶部有包件选择器（显示包件名与条目数）。项目尚未启用包件时保持旧界面，点击
  「启用包件」输入名称即可创建首个包件；**首个包件会自动收养**项目原有的单份清单快照。
- 「管理包件」弹窗可新增、改名、删除包件，并显示每个包件是否已有清单。
- 上传清单、对齐差异、逐行报价、忽略/恢复与导出都只作用于当前包件；切换包件会重新加载
  该包清单，空态提示「该包件尚未上传清单」，不会把别的包数据混进来。
- 分包导出文件名带包件名：`{项目名}-{包件名}-清单响应表.xlsx`；未启用包件时仍用旧文件名。
- 删除包件会同时删除该包的清单快照、`role=boq` 的原件记录与磁盘文件，不可撤销；
  只读成员不能做任何包件写操作。

## 定额库与调价

`/admin` → **定额库** 维护企业自己的定额单价（名称、规格、单位、单价、分类、备注），
支持按名称/规格/分类搜索，以及用名称+规格做「匹配测试」查看相似度前几名。
单价必须为非负有限数，名称必填。该库是全局数据，只有超级管理员可增删改。

- 清单页「定额套用」先做 **dry-run 预览**：按清单行名称（规格加分）与定额库匹配，
  列出建议单价与相似度，默认勾选全部；确认后才把勾选项写入当前包件的清单单价。
  「仅填补未报价行」默认开启，避免覆盖已人工录入的价格。
- 程序不会凭空生成价格：只套用管理员维护的定额单价，匹配不到就保持原样。
- 清单页「调价」折叠面板维护项目调价策略：启用开关、系数（0.1–10）、小数位（0–4）。
  启用后清单报价汇总显示「调整后合计」，导出响应表的「报价汇总」增「调价系数」与
  「调整后合计（元）」两行；未启用时不增行。
- 「按系数调价」会把当前包件所有已录入单价乘以系数并按小数位四舍五入后写回，
  **不可撤销**，操作前会二次确认；没有已录入单价时返回错误。调价与策略变更均记审计。

## 插件管理

`/admin` → **插件** 让 BidCraft 作为 MCP 客户端接入外部 MCP server，并把它们的工具聚合进
`bidcraft mcp` 的 `tools/list`。新库不预置任何插件（插件表为空），需超管显式添加；
单个插件可随时停用，停用后不再出现在工具列表。

- 支持 `stdio`（填写命令、参数、环境变量）与 `http`（填写 JSON-RPC 端点 URL）两种传输；
  名称唯一且不能含 `__`（工具名前缀分隔符）。
- 新增弹窗提供预设模板：filesystem、fetch、memory、time。**预设只是模板，不会自动安装**，
  选中后仍需确认命令/目录/URL 并显式保存；`npx`/`uvx` 首次运行需要联网下载。
- 「测试」会实际握手并展示可用工具名，结果（成功/失败/信息）写回该插件；失败不会返回 5xx。
- 工具白名单为空表示暴露该插件全部工具；填写后只列出/允许白名单内的工具。所有插件变更与
  测试都记审计。
- **资源限制（仅 stdio 插件生效）**：内存上限（64–4096 MB，默认 512）与 CPU 时间（1–120 秒，
  默认 10）。子进程以 RLIMIT_AS/RLIMIT_CPU 强制执行，umask 077，且每次运行使用一次性临时
  工作目录（结束后删除）；越界或非法值入库时回退默认，不报错。
- `BIDCRAFT_PLUGIN_TIMEOUT` 控制单次请求超时（秒，默认 20，范围 5–120）；首次下载慢时可调大。
- **插件包导入/导出**：每行「导出包」下载 `<名称>.bidplugin.zip`（内含 `manifest.json`，
  含全部配置、作用域与环境变量，**注意 env 为明文**）；工具栏「导入插件包」上传校验后创建新插件
  （201）或对同名插件覆盖升级（200），导入记审计 `plugin.import`。包可用可选 Ed25519 签名：
  导出端配 `BIDCRAFT_PLUGIN_SIGNING_KEY` 即自动签名，导入端配 `BIDCRAFT_PLUGIN_TRUSTED_KEYS`
  验签；需要强制验签时设 `BIDCRAFT_PLUGIN_REQUIRE_SIGNATURE=1` 或导入请求带
  `?require_signature=true`（有签名但无信任公钥会拒绝导入）。
- 聚合规则：本征 6 个工具在前，插件工具命名为 `{插件}__{工具}`；单个插件握手失败只会在
  服务端 stderr 打一行警告并跳过，不影响其他工具；`--readonly` 的 MCP 端点拒绝所有插件工具。
- **安全提示**：插件以 BidCraft 进程的操作系统用户身份运行本机子进程，或向管理员填写的 URL
  发请求；已有应用层资源限制、HTTP 出站地址防护与作用域隔离，但**没有容器/系统级隔离**。
  只配置可信插件；插件 `env` 明文存库，不要放长期密钥。细节与排错见 [`docs/plugins.md`](plugins.md)。

## 回归校准

`bidcraft calibrate` 用真实或仿真招标文件目录跑一遍解析与抽取，用来判断该补别名、补规则包
还是需要 OCR。命令**只读文件系统**：不写数据库、不创建项目、不调用模型。

```bash
bidcraft calibrate /path/to/tenders
bidcraft calibrate /path/to/tenders --recursive --output /tmp/calibrate-report.json
```

- 扫描 `.pdf` `.docx` `.txt` `.md/.markdown` `.xlsx/.xlsm`；默认不递归。
- 报告分 `per_file` 与 `aggregate`：每文件给出页数、表格数、材料行、已填/必填/缺失必填事实、
  警告、`needs_ocr` 与 `error`；汇总给出 `files/ok/failed`、`field_hits`、
  `required_hit_rate`（0–1）、`avg_materials`、`ocr_files`。
- 单个文件失败只记 `error` 并继续，命令仍以 0 退出；目录不存在以 1 退出并提示中文错误。
- 字段命中率低时先补 `parsing/extract.py` 的通用别名，行业规则改对应规则包；
  `facts_missing_required` 高要核对原件是否真的缺失；`needs_ocr=true` 需安装 OCR 依赖。
- 仓库内 `tests/fixtures/regression/` 是**仿真件**，用于回归别名与抽取口径；真实招标文件含
  商业信息，应由用户放入独立目录运行，不提交仓库。报告字段与处理步骤见
  [`docs/calibration.md`](calibration.md)。

## MCP 接入

`bidcraft mcp` 以 stdio JSON-RPC 暴露 6 个工具（list_projects、get_project、get_ledger、
run_check、export_document、search_knowledge），供 Claude Desktop / Cursor 等 MCP 客户端
调用；`--readonly` 禁用 run_check 与 export_document。配置示例与工具契约见
[`docs/mcp.md`](mcp.md)。stdio 进程信任本机用户，请把 `BIDCRAFT_HOME` 指向目标数据目录。

## 生成时的行为

1. 解析招标文件，建立事实台账并人工校订。
2. 规划大纲；正文生成时解析默认对话模型。
3. 每章按“章节标题 + 意图”检索启用的知识库，取最多 4 条片段加入提示词。
4. 未配置可用对话模型时，自动使用确定性草稿，不编造事实。
5. 核对与导出不依赖模型；导出 DOCX/PDF/XLSX 始终可用。

## 部署与安全

- 单机：`bidcraft serve --open`，仅监听 `127.0.0.1`。
- 局域网：`bidcraft serve --host 0.0.0.0`，建议放在带认证的反向代理之后并启用 HTTPS。
- 反向代理终止 TLS 时设置 `BIDCRAFT_SECURE_COOKIE=1`，会话 Cookie 仅经 HTTPS 发送。
- 会话 Cookie 为 HttpOnly、SameSite=Lax；密码使用 scrypt 加盐哈希；登录失败按用户名限流。
- 系统无遥测；除显式配置的模型与知识库端点（以及图片端点返回的临时下载 URL）外
  不发起外部请求。
- 公开 `/health` 只返回 `status` 与前端必需字段（不含版本、路径、计数），便于探活且不泄露部署细节；
  排障与确认版本用 `/admin/health`（仅超级管理员，返回版本、启动时间/uptime、Python 与平台、
  数据库大小与磁盘余量、模型/知识库/用户计数及 `docs_enabled` 等开关）。
- 项目级成员权限与操作审计已内置：owner 管理成员，写操作按 editor/viewer 门禁，
  关键操作写入 `audit_logs`（项目页「协作」与管理端「审计日志」可查）。
  公网多人场景仍建议配合反向代理与网络隔离。

## 微信开放平台

`/admin` →「微信开放平台」可配置扫码登录，保存后立即生效（无需重启）：

- **AppID / AppSecret**：开放平台「网站应用」凭据。密钥使用 `secret.key` 加密入库，接口只返回 `has_secret`，不回显明文；可勾选「清除已保存的密钥」。
- **授权回调地址**：必须与开放平台登记的授权回调域一致，且为公网可达的 HTTPS 地址。
- **启用微信扫码登录**：关闭时 `/health.wechat_login=false`，登录/注册页不显示微信入口，`/auth/wechat/start` 返回 400。
- **模拟模式**：不访问微信服务器，扫码跳转 `/auth/wechat/mock` 生成本地测试账号，用于内网联调。
- 「测试连通性」在模拟模式下直接通过；真实模式下校验三要素完整并探测开放平台可达性。
- 配置优先级：管理页（数据库）> 环境变量 `BIDCRAFT_WECHAT_APP_ID/APP_SECRET/REDIRECT_URI`、`BIDCRAFT_WECHAT_MOCK`。仅管理页启用后来源显示为「管理控制台」。
- 所有修改记审计 `wechat.config`（仅超级管理员）。

## 企业术语库

`/admin` → **术语库** 维护公司统一表述：

- **禁用表述**：正文命中即产出核对问题，级别 `major`；
- **建议替换**：命中且未统一为推荐写法时产出 `minor` 建议；
- 两者类别均为「术语规范」，编号 `TERM-001` 起递增，证据含 `source/target/quote`（原文截取 ≤80 字）；
- 跨章节按（级别 + 原表述）去重，单次核对最多 200 条；停用（`enabled=false`）的术语不参与核对；
- 列表支持搜索与类型筛选，编辑弹窗可改类型/原表述/推荐表述/备注/启用，删除会二次确认（可改为停用）；
- 所有修改记审计 `term.create` / `term.update` / `term.delete`（仅超级管理员）。

## 报价审批链

项目报价支持多级审批与并行会签（R18/R19）。在「清单与报价 → 报价版本」面板：

- **配置审批链**（仅项目负责人）：工具栏「审批链」按钮打开设置弹窗，按顺序添加审批级（最多 5 级，可上移/下移/移除）；每级可加 1–5 名审批人（负责人与可编辑成员），并选择模式——**会签（全部通过）**或**或签（任一通过）**；每级还可选填**金额门槛**（留空=恒生效）。保存后项目 payload 回显 `approval_chain`（阶段列表）。名称为配置时的快照，成员改名不追更；旧版扁平链自动按单审批人会签级兼容。
- **未设置审批链**：保持单级审批——负责人或超级管理员定稿/驳回（R14 行为）。
- **逐级流转**：提交后按链顺序审批，非当前级审批人（且非超管）审批返回 403；会签级需本级全部审批人通过才推进（已批者重复审批返回 403「您已完成本级审批」），或签级任一人通过即推进；中间级通过后版本仍为待审；末级通过才定稿（同包件旧定稿自动退回草稿）；任一级驳回即终止，重新提交会清空已积累的审批记录。
- **金额门槛条件级**：设了门槛的审批级仅在报价总额 ≥ 门槛时生效，低价版本自动跳过该级（「第 X/N 级」的 N 按生效级数计算）；金额未知时保守视为生效。
- **包件/币种条件级**：每级还可设「适用包件」（包件 id 白名单）与「适用币种」（如 CNY/USD/EUR，大小写不敏感，支持自定义）；仅当版本的包件、项目的币种命中白名单时该级才生效，留空=不限。三条件（金额/包件/币种）可组合，任一不命中即跳过；若全部审批级都被条件过滤掉，则回退为全部级别均生效。审批记录仍按原链级别存档，时间线不受跳级影响；待我审批待办同样按生效序列过滤。
- **可见性**：版本行显示「第 X/N 级待审」徽标、待批名单（会签级为尚未通过者）与审批时间线（级别/审批人/意见/时间）；当前级待批审批人或超管才看到审批按钮，其他人显示「等待「审批人」」；会签未完结时提示「会签进行中，还需 X 通过」。
- 超级管理员可在任意级代审（会签级可代批多人）；所有审批动作记审计（含级别与结果状态）。
- **待我审批**：顶栏「待我审批」入口汇总当前用户可见项目中轮到本人审批的待审版本（空链=负责人；链式=当前级审批人且会签尚未批；超管可见全部），数量徽标 + 只读面板显示项目/版本/级别/模式/提交人/金额，点击直达该项目「清单对齐」页签完成审批；面板打开时每 60 秒轮询刷新。

## VIP 会员与子账号

**VIP 会员**（超级管理员在 `/admin` → 成员 授予）：

- 「VIP」操作为成员授予会员资格，天数 1–3650（`0` 清除）；续期在当前到期时间上累加，未到期则从当前时间起算。子账号继承主账号 VIP，不能单独设置。
- VIP 权益：充值/生成消费按 **vip_discount**（默认 0.5，即半价，向上取整到整数点）打折；VIP 名下用户提交的后台任务（批量核对/导出、配图、正文生成）进入**优先级队列**并优先执行。
- 用户也可自助购买 VIP 套餐（`/billing` → VIP 套餐），走与充值相同的微信/mock 支付流程；VIP 订单**只延长会员有效期、不增加点数**（流水 kind=`vip`、金额 0）。
- 后台在 `/admin` → 计费 可维护 **VIP 套餐**（名称/天数/价格）、**vip_discount**（0.1–1）与**子账号上限**（sub_account_limit，0–20）。
- 授予/续期/清除 VIP 记审计 `user.vip`。

**子账号**（会员自助在 `/billing` 管理）：

- 仅 **VIP 生效的主账号**可创建子账号，数量受 sub_account_limit 限制；子账号为普通成员（manager）、自助注册属性、点数 0。
- 子账号**共享主账号点数余额**：其消费按 VIP 折扣计入主账号，流水备注标注「子账号 {用户名}」。子账号**不能单独充值/兑换/购买 VIP**（返回 403）。
- 主账号可停用/启用子账号、重置其密码、删除子账号；**删除子账号会将其名下项目移交回主账号**。
- 子账号的创建/修改/删除记审计 `account.sub_create` / `account.sub_update` / `account.sub_delete`。

## 我的文档（个人知识库）

普通用户在顶栏或账号菜单进入「我的文档」（`/my-docs`），可自助上传文件到服务器个人目录并由系统自动建索引：

- 支持拖拽/选择多个文件，后缀白名单与单文件 ≤50MB 校验，逐文件显示上传进度。
- 每个用户拥有独立的**个人知识库**（目录 `BIDCRAFT_HOME/user_docs/{user_id}/`，KB 选项 `options.personal=true`）；上传成功即写入文件、建立/复用个人 KB 并后台启动重建索引任务（列表状态显示「索引中 / 可检索 / 索引失败」）。
- 生成正文时**只注入当前用户自己的个人文档**，且全局知识库检索默认排除所有个人库，避免跨用户泄漏；用户只能查看/下载/删除自己的文档。
- 上传/删除记审计 `user_doc.upload` / `user_doc.delete`；删除文档不立即重建 KB，其残留片段在下一次重建索引时清除。

注：系统级知识库（`/admin` → 知识库）仍为超级管理员维护；「本地目录」类型填写的是**服务器上的文件系统绝对路径**（如 `/srv/bidcraft/knowledge/tender-archive`），不是用户本机路径或 http 地址；要接第三方检索请选「API/第三方接口」类型。

## 素材可信度分级（material_policy）

知识库只判断「命中」不够，还要判断「可信」。规则包（`common-bid-facts.yaml`）里的
`material_policy` 为每类素材声明必填的生命周期字段：

| 素材类型 | 必填字段 |
|---|---|
| 资质证书 `qualification` | 证书编号、有效期至 |
| 业绩合同 `performance` | 合同编号、业主、金额、验收结论 |
| 人员证书 `personnel` | 证书号、社保缴纳月份、在建锁定 |
| 标准规范 `standard` | 官方出处 |

行为：

- 管理端为知识库中的每个来源登记元数据：`PUT /admin/kbs/{id}/docs`（`source`、`kind`、`title`、`valid_to`、`source_url` 等）
- 检索注入时：字段齐全且在有效期内 → 注入正文；缺字段或已过期 → **降级为题录**（只给标题、有效期、出处），模型不得据其复述细节
- 有效期按 **北京时间日历日**（UTC+8）判定，与服务器进程时区无关；否则北京时间 00:00–08:00 会把昨天到期的证书判成未过期
- `kind` 缺失或不在当前策略里（拼错、覆盖包被隐藏、旧版本元数据）一律**失败关闭**为「未知素材类型，未注入正文」；写入侧同样必填，缺省不会静默归为「其他素材」
- 「其他素材」不是免检通道：必须填**官方出处或来源链接**（`source_url`），否则同样降级为题录。分类为「其他」但实际是资质/业绩的扫描件，仍需改到正确类型并补生命周期字段，否则不会进入正文
- 判定结果可在 `GET /admin/kbs/{id}/docs` 查看（`ok`/`reason`）
- 未登记元数据的来源一律按题录处理——宁可少注入，不让过期证书进入正文


## 文本规则（错别字词库）

`/admin` → **文本规则**：

- 内置 12 组高置信错词（帐号→账号、部份→部分、按装→安装等）不可删除；
- 自定义规则优先于内置（同一错词以自定义「改为」为准），命中写入问题台账 `TXT-###`，证据标记 `custom: true`；
- 上限 500 条、错词/改为各 ≤20 字、备注 ≤60 字；保存后下一次核对即生效；
- 所有改动记审计 `textqa.config`。


## 注销冷静期与删除审计

- 用户提交注销需**密码 + 输入「注销」**，进入 **7 天冷静期**；期间账号仍可登录，页面显示剩余天数与可撤销按钮。
- 冷静期内撤销即恢复；再次申请会重置到期时间。
- 到期后由运维执行删除：
  ```bash
  bidcraft purge-accounts --dry-run   # 先看到期名单
  bidcraft purge-accounts             # 真正删除
  ```
  或超管调用 `POST /admin/accounts/purge?dry_run=1`。
- 有子账号的主账号不会被自动删除（返回 skipped），需先处理子账号。
- 每次执行写审计 `account.purge`：用户名、申请/到期时间、删除的项目/文档/资质/人员/流水数量；批量调用另记 `account.purge_batch`。
- 建议 cron 每日跑一次；审计记录不随用户删除而清除，保留追责依据。


## 运行状态与运营指标

管理控制台「运行状态」页读取 `GET /admin/health`（仅超管，公开 `/health` 刻意保持最小化）：
服务版本与启动时间、运行时长、Python/平台、数据目录与磁盘余量、模型/向量模型配置、
模型/知识库/账号数量、前端构建产物是否就绪、离线/文档页/注册/安全 Cookie/微信登录与支付
等开关。页面顶部有手动刷新按钮。

README 声明的三项质量指标由项目数据计算，当前没有全站聚合接口，因此页面只列出定义与
「暂无全局聚合」，不引用未经测量的数字；后端若在 health 响应中补充 `metrics`
（`manual_edit_rate` / `issue_density` / `boq_match_rate`），页面会自动显示对应值：

| 指标 | 口径 |
|---|---|
| 人工修改率 | 章节 `revision > 1` 的比例，及修改字数 / 生成字数 |
| 核对问题密度 | 核对产出的问题数 ÷ 正文字数 |
| 清单匹配率 | 清单行匹配到台账材料的比例，含缺项/多项 |

## 开票与条款同意

- 注册必须勾选同意《服务条款》《隐私政策》，系统记录版本与时间（`terms_version`、`terms_accepted_at`），便于合规举证；条款更新后 `GET /legal/versions` 返回当前版本。
- 用户提交开票申请（抬头、税号、邮箱、金额、备注）→ `/admin/invoices` 查看待开具 → 上传 PDF/图片并填写发票号即完成开具；也可填原因驳回，用户端显示驳回原因并可重新申请。
- 管理控制台「计费与充值」页的「开票申请」卡片已接入上述接口：列表展示申请人、抬头、金额、状态与发票号，待开具项可点「开具」（发票号 + PDF/PNG/JPG 文件，≤10MB）或「驳回」（必填原因）；提交后自动刷新列表并给出成功/失败提示。文件必须由管理员在本地准备好后上传，系统不接第三方开票服务。
- 审计：`invoice.request` / `invoice.issue` / `invoice.reject`。
- 对账单（`GET /billing/statement`）的「时间」列与 `start`/`end` 过滤都按北京时间日历日，凌晨 00:00–08:00 的流水不会被算到前一天。
- 备份默认保留 10 份：`bidcraft backup-prune --keep 10 --dry-run` 先看名单，再去掉 `--dry-run` 执行。隐私政策已说明备份轮转期内的数据保留。
